# RFC-014.5 — Output Collision Strategies

## Status

Implemented

## Dependency

This RFC extends:

* `RFC-014 — Parallel Snapshot Execution`

RFC-014 introduced bounded concurrent execution for snapshot jobs.

A post-implementation audit identified that two valid jobs may legitimately resolve to the same output path when executed concurrently.

This RFC defines how SnapRun detects, schedules and resolves output collisions while keeping the scheduler completely generic.

---

# 1. Summary

Parallel execution allows multiple snapshot jobs to execute simultaneously.

This introduces a new class of problem:

```text
Job A
↓

snapshots/run/dashboard.png

Job B
↓

snapshots/run/dashboard.png
```

If both jobs execute concurrently, the resulting screenshot becomes nondeterministic.

The scheduler itself should not solve this problem.

Instead, SnapRun must detect output collisions during execution planning and apply a configurable collision strategy.

---

# 2. Goals

This RFC introduces:

* deterministic output collision detection;
* configurable collision strategies;
* interactive conflict resolution;
* CI-safe behaviour;
* resource-aware scheduling.

This RFC must not reduce parallelism for jobs that do not conflict.

---

# 3. Non-goals

This RFC does not introduce:

* browser pools;
* retries;
* worker threads;
* distributed execution;
* cancellation;
* priority queues;
* adaptive scheduling.

Those remain outside the scope of RFC-014.

---

# 4. Collision Definition

Two jobs are considered to be in conflict when:

```ts
computeSnapshotFilePath(jobA) === computeSnapshotFilePath(jobB)
```

The collision key is therefore the fully resolved output path.

It is intentionally **not** based on:

* route id;
* run id;
* scope;
* user;
* execution order.

Any future output structure automatically benefits from the same mechanism.

---

# 5. Execution Model

The scheduler continues to execute jobs.

Collision management is performed before jobs are submitted.

```text
Execution Plan
        │
        ▼
Resolve Output Paths
        │
        ▼
Detect Collision Groups
        │
        ├─────────────┐
        ▼             ▼
 Safe Jobs      Collision Queue
        │             │
        ▼             │
Bounded Scheduler     │
        │             │
        ▼             ▼
 Normal Output   Collision Resolution
                      │
                      ▼
                 Final Report
```

The scheduler remains completely unaware of:

* SnapRun runs;
* routes;
* screenshots;
* output structures;
* CLI prompts.

It only schedules executable jobs.

---

# 6. Configuration

Introduce:

```json
{
  "execution": {
    "concurrency": 4,
    "collisionStrategy": "prompt"
  }
}
```

Supported values:

```text
prompt
serialize
error
```

Default:

```text
prompt
```

for interactive sessions.

---

# 7. Collision Strategies

## error

Execution stops before any conflicting screenshot is produced.

Example:

```text
Output collision detected

snapshots/run/dashboard.png

Conflicting jobs

- member/dashboard
- admin/dashboard
```

Recommended for:

* CI;
* automated pipelines;
* deterministic builds.

---

## serialize

Jobs targeting the same output path are executed sequentially.

Jobs targeting different output paths remain fully parallel.

Example:

```text
A -> dashboard.png
B -> dashboard.png
C -> account.png
D -> settings.png
```

may execute as:

```text
A ─────── B
C ─────────
D ─────────
```

Only the conflicting resource is serialized.

Global concurrency is still respected.

---

## prompt

Safe jobs execute immediately.

Conflicting jobs are placed into a dedicated collision queue.

Once the normal queue finishes, SnapRun prompts the user.

Example:

```text
3 output collisions detected.

dashboard.png
  - member
  - admin

Choose a strategy

> Re-run sequentially
  Overwrite sequentially
  Create subfolders
  Skip
```

---

# 8. Interactive Actions

## Re-run sequentially

Execute conflicting jobs sequentially.

The existing execution order determines which result remains on disk.

---

## Overwrite sequentially

Explicitly accept that later jobs replace previous outputs.

Concurrent writes remain forbidden.

---

## Create subfolders

Generate unique output directories for conflicting jobs.

Example:

```text
snapshots/

run/

member/
    dashboard.png

admin/
    dashboard.png
```

Folder names must be deterministic.

Random identifiers are forbidden.

---

## Skip

Skip the conflicting jobs.

Skipped captures appear explicitly in the execution report.

---

# 9. Resource-aware Scheduling

For:

```text
collisionStrategy = serialize
```

the resource identifier becomes:

```ts
resolvedOutputPath
```

Invariant:

> At most one active job may own a given output resource.

This constraint exists in addition to:

```text
execution.concurrency
```

---

# 10. Non-interactive Environments

Interactive prompts must never block execution indefinitely.

If prompting is unavailable:

```text
prompt
```

falls back automatically to:

```text
error
```

This guarantees deterministic CI behaviour.

---

# 11. Failure Semantics

Output collisions are **not** snapshot failures.

Depending on the strategy:

* `error` → planning error;
* `serialize` → normal execution;
* `prompt` → user decision;
* `skip` → skipped result.

They should appear separately from capture failures.

---

# 12. Tests

The implementation must include deterministic tests covering:

## Collision detection

* identical paths;
* different paths;
* multiple collision groups;
* no collisions.

## serialize

* conflicting jobs never overlap;
* unrelated jobs remain parallel;
* concurrency limit is respected;
* deterministic overwrite order.

## error

* execution aborts before capture;
* error lists conflicting jobs;
* no screenshot is written.

## prompt

* collision queue creation;
* sequential replay;
* subfolder generation;
* skip handling;
* non-interactive fallback.

Timing-based assertions should be avoided whenever deterministic synchronization primitives are available.

---

# 13. Acceptance Criteria

This RFC is complete when:

* output collisions are detected before execution;
* collision groups are built from resolved output paths;
* `execution.collisionStrategy` supports `prompt`, `serialize`, and `error`;
* conflicting jobs never write concurrently to the same file;
* unrelated jobs retain full parallel execution;
* interactive prompting never blocks CI;
* subfolder generation is deterministic;
* collision handling remains outside the scheduler;
* all behaviours are covered by deterministic tests.

---

# 14. Future Work

Potential future extensions include:

* custom naming strategies for collision folders;
* automatic merge strategies;
* collision reporting formats;
* interactive batch resolution;
* persistent collision policies;
* plugin-provided collision handlers.

These features are intentionally outside the scope of this RFC.
